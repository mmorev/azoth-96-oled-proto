Файл: `Device_FW/M901_DEVICE_V07_00_30.bin` (643 072 байта), версия FW **V07.00.30**.

## 1. Формат файла прошивки

Это **не** сырой дамп, а мульти-образный **SUIT DFU-пакет** (CBOR, Nordic nRF54H20):

```
0x00000  SUIT Envelope (CBOR tag 107):
           key 2  = SHA-256 манифеста
           key 3  = манифест-последовательность (839 B): компоненты cMEM/CAND_MFST/INSTLD_MFST,
                    Nordic vendor UUID 7617DAA5-71FD-5A85-8F94-E28D735CE9F4
           key "#radio"       → payload 405 247 B (вложенный SUIT envelope + бинарник)
           key "#application" → payload 135 151 B (аналогично)
0x00384  payload #radio:      вложенный envelope {manifest, buildinfo, бинарник 404 660 B}
0x63295  payload #application: вложенный envelope {manifest, buildinfo, бинарник 134 532 B}
0x84200…0x9CFFF  нулевое заполнение
```

Извлечённые бинарники (лежат в `analysis/`, SHA-256 совпадает с дайджестами в манифесте):

| Бинарник | Размер | Адрес (radio window) | Адрес (app window) | Что это |
|---|---|---|---|---|
| `m901_keyboard_app.bin` | 404 660 (0x62CB4) | **0x0E066000** | 0x0006F000 | **Клавиатурное приложение** (Zephyr RTOS + BT host + SoftDevice Controller + HID + RGB + дисплей) |
| `m901_sysctrl.bin` | 134 532 (0x20D84) | 0x0E0D5000 | **0x00029000** | Nordic system-controller (icmsg IPC, `Calendar`/`SystemInfo`/`LightData` — дисплейная часть) |

Железо: **Nordic nRF54H20** (2× Cortex-M33 + FLPR), Zephyr/ NCS, BLE (SoftDevice Controller),
USB FS+HS (`FS Configuration`, `HS Configuration`), 4 HID-интерфейса (`hid_dev_0..3`).
Строки: `ROG AZOTH`, `ROG AZOTH 96 HE`, `ASUSTeK`, SDK вендора — `dragoon/libs/...`.

## 2. USB / HID транспорт

**Device descriptor: VID = `0x0B05` (ASUS), PID = `0x1C10`**, bcdUSB 2.00, класс EF/02/01 (IAD composite), EP0 = 64.
Шаблоны дескрипторов в образе: 0x0E0C68C4 (FS) и 0x0E0C68D8 (HS). Строки: `ASUSTeK`, `ROG AZOTH 96 HE`, `FS/HS Configuration`.

| hid_dev_1 | 0x01 / 0x0C / **0xFFC0** | мышь (ID 4), system control (ID 2), consumer 20 бит (ID 3/1), **vendor 0xFFC0: Report ID 3, 20 байт IN** | Мышь/медиа + сервисный канал 20 B |

## 3. Vendor-протокол (64-байтный канал 0xFF00/0xFF01)

Вся обработка — в `m901_keyboard_app.bin` (база **0x0E066000**, ниже адреса абсолютные).

### 3.1 Разблокировка (magic)

При старте часть команд закрыта «гейтом» (0x0E090658). Хост посылает:

```
7B AA 41 53 55 53 AA 00 … 00        # "{", 0xAA, 'A','S','U','S', 0xAA  (ASCII "ASUS" в фигурных скобках)
```

Устройство: считает контрольную сумму пакета (0x0E081590), пишет флаг **0xDEADBEEF** по адресу
0x0E1A3600 (flash-область boot-запроса) и **ребутится в bootloader** (строка лога "enter bootloader",
команда 0x0E090604, потом sys_reboot 0x0E095440).
После магии гейт разрешает команды: **0x61, 0x62, 0x67 (с arg[1]==2), 0x6B, 0xC0**.

> Это одновременно и «вход в bootloader» для прошивки через `peripheral_fwu_pro.exe`.

### 3.2 Формат пакета запроса (64 B)

```
offset 0   u8   CMD     — старшая команда (см. таблицу)
offset 1   u8   SUB     — подкоманда
offset 2   u16  ECHO    — возвращается в ответе как есть (counter/id)
offset 4   …    ARGS    — аргументы (до конца 64 B)
```

### 3.3 Формат ответа (64 B IN)

Строится функцией 0x0E078DEC:

```
offset 0   u8   RCMD    — код-ответ (0x12/0x24/0x25/0x27/0x41/0x43/0x51 …)
offset 1   u8   SUB     — подкоманда/статус
offset 2   u16  ECHO    — эхо из запроса
offset 4   …    PAYLOAD — копия ≤60 байт из внутреннего состояния
```

Ошибка/NAK: функция 0x0E078E74 шлёт `FF AA <cmd:u16>` (встречается как ответ на неизвестные команды).

Транспортный слой: OUT-данные попадают в кольцевой буфер 0x1000 байт
(0x0E090984 putc / 0x0E0909A0 drain / 0x0E0909F8 flush, чанки ≤0x40),
собранный пакет кладётся в буфер 0x2300CB1C и обрабатывается **главным диспетчером 0x0E07A63A**
(работает как polling-таск). Ответ уходит через очередь 0x0E091E90 (queue id 2).

### 3.4 Карта команд (главный диспетчер, switch по CMD)

**Диспетчеризация (исправлено 2026-10-02, пере-проверено 2026-10-03 по полной выгрузке
и по байту таблиц в образе):**
блок 0x0E07AB74: после проверки диапазона
`sub r3, r0, #0x21; cmp r3, #0xD9; bhi NAK` идёт `ldr.w pc, [r2, r3, lsl #2]` — таблица
`@0x0E07AB9C` это **главная таблица хостовых опкодов** (индекс = opcode − 0x21, **218 слотов,
0x21..0xFA**). Активные опкоды таблицы (пустые слоты = 0x0E07A704 NAK): 0x21–0x25, 0x27, 0x41,
0x43, 0x50–0x54, 0x61–0x6B (0x61–0x67/0x6A/0x6B через гейт 0x0E07A7AB, 0x68/0x69 отдельно),
0x71–0x74, 0x80, 0xB0, 0xC0, 0xFA. **Вне таблицы** диспетчер (0x0E07A6CE..0x0E07A704)разбирает:
`0x12` → jt @0x0E07A744; `0xC0` → 0x0E07A7D0 (sub 0x81/0x83); диапазон `0x63–0x67` → гейт
0x0E07A7AA → 0x0E08CE6C; `0xFB` → 0x0E07CCBE (лог-канал); `0xFD` → 0x0E07A6F4 (sub 0xA0/0xA1 →
0x0E07D306, sub ≥0xA2 → 0x0E07CD5C, прочие sub → NAK); `0xFC`, `0xFE`, `0xFF` → 0x0E07D592 (NAK).
Всё прочее в таблице → 0x0E07A705 = NAK `FF AA <cmd:u16>`. Ответы устройства используют коды
0x24/0x25/0x27 — те же байты, что и опкоды хост→клава (пространство общее, смотри направление).
**Полная выгрузка с адресами обработчиков — `PROTOCOL_VOLUME.md` §6** (там же sub-таблицы
0x51 @0x0E07B318 — 145 слотов и 0x25 @0x0E07B56C — 39 слотов; @0x0E07BD44 — sub-таблица
опкода 0x23, 5 слотов: [1]=NAK, [2..4]=sub 2/3/4).

### 3.5 RGB-подсистема (опкоды 0x25 / 0x51 — исправлено 2026-10-02)

> **ВАЖНО (перепроверено 2026-10-03 ещё раз, по декомпиляции Ghidra):** всё, что в старых
> версиях этого дока и в `handlers_all.txt` помечено как «CMD 0xFD g2», на самом деле
> маршрутизируется опкодами **0x25** (get-семейство, хендлер 0x0E07B55C, таблица sub
> @0x0E07B56C) и **0x51 sub 0x21/0x22** (set-color 0x0E07BFC0).
> **Уточнение к предыдущей редакции:** опкод 0xFD диспетчером обслуживается — но отдельной
> веткой ВНЕ jump-таблицы (`cmp r0,#0xFD` @0x0E07A6EE → sub-обработка 0x0E07A6F4, см. §3.4),
> а НЕ через таблицу @0x0E07AB9C. Через саму таблицу 0xFB–0xFF не проходят (там только
> 0x21..0xFA). «FD»-разметка таблиц @0x0E07B56C/@0x0E07BD44 относится к опкодам 0x25/0x23 —
> это просто соседние данные, а не ветки 0xFD.
> Соответствие: «FD 00/01 [dev]» = `25 00/01 [dev]`; «FD 03» = `25 03`; «FD 04» = `25 04`;
> «FD 02» = `25 02`; «FD 22» = `25 22`; «FD g2 sub 0x22→0x0E07BF72/0x0E07BF52» = самостоятельные
> опкоды 0x41/0x43; «FD sub 0x34 (set-цвет)» = `51 21/22 …`.
> Адреса обработчиков в таблице ниже верные, изменились только номера опкодов.

Ключевые структуры RAM:
- `0x23008EF4` — таблица LED-«профилей»: записи по **60 байт** (0x3C), слои по смещению `layer*0x1C24`:
  `+0x04` u8 режим (0/1/2), `+0x0C` u8 dirty=1, `+0x0D` u8 time (pkt/10), `+0x0E` 12-бит цвет

- LUT: `0xE0C1188` (HID usage → LED-позиция, 196 записей), `0xE0C125C` (HID usage → matrix idx),

(слои), не N именных профилей; сохранение онборд — семья `0x80 sub 0x20..0x27` (флеш 0x0E081988).

#### 3.5.1 Два слоя per-key и рендер-конвейер (разобрано 2026-10-03, Ghidra + дизассембл)

**Слои.** Байт layer в `51 21/22` и `25 02/04` — только **`0x00`** (слой 0) или **`0x9F`**
(слой 1), прочее = NAK (проверено: `0x0E07BFC2` `ldrb [pkt,#3]`, `0x0E07BC1A` `ldrb [pkt,#5]`).
Индекс слоя множится на `0xF7` в таблице цветов и `0x1C24` в профилях — две **полные
независимые per-key схемы**. `0x9F` — не случайность: это код спец-клавиши в кодовом
пространстве ASUS (FUN_0e078604 @0x0E078604: key `0x9F` → LED-слот 0x7F, key `0xD3` → 0x40;
в luts.json `matrix_lut[0x9F]`/`meta_lut[0x9F]` заполнены) — слой 1, судя по всему,
**подсветка слоя Fn** (стандартная модель ASUS Layer 0 / Layer 1-Fn).

**Рендер.** Ядро приложения **всегда** считает и выгружает оба слоя: FUN_0e082a74
(0x0E082A74) кладёт цвета обоих слоёв в рендер-структуру (блоки шагом 0x6E у +0x804/+0x8E0;
у dirty-клавиш — цвет из таблицы, у остальных — текущий цвет эффекта из `0x23014B14+dev*8`),
FUN_0e081ef0 (0x0E081EF0) заливает структуру целиком (0xDD8 Б) LED-контроллеру по шине
**0x10000**, FUN_0e082fa8 (0x0E082FA8) вдогонку шлёт `{1, селектор}` (→ FUN_0e0837e8).
**Селектор страницы** — u32 `[0x23015EF8+8]`; единственная запись на весь образ —
FUN_0e09587c (0x0E09587C): байт из конфиг-блока внешнего контроллера (шина 0x13000,
зеркало 0x23010A80) → флеш-таблица **0x0E0C39BC** (26 входных значений → {0,1}; страницы
RAM-LUT 0x23000B38 по 0x80 записей различаются 2 ячейками сетки 5×22 — похоже на вариант
раскладки). Хост меняет конфиг-байт командой через диспетчер (путь 0x2300CB20 →
FUN_0e081c3c). **Нажатие Fn в этом образе селектор не трогает** — финальный выбор
«какой слой показывать» происходит на стороне LED-MCU (его прошивки у нас нет; в sysctrl
рендера нет — только строка `LightData` для дисплейного виджета) либо задаётся тем самым
конфиг-байтом. Открытый вопрос закрывается экспериментом: покрасить клавишу в слое 1,
зажать Fn, сравнить.

**Кодировка spec (pkt[4..5]) в set-color** — немедленная запись в таблицу цветов:
`≤0xBC` → значение `LUT[pkt4]` (похоже на градиент по LED-позиции); `≥0x306` → прямой
12-битный цвет; low-байт `0xFF` → спец-таблица (DAT_0e07f560, та же схема `+0xD4`);
прочее → `0xA000|(lo+0xE6)` в таблицу эффектов (DAT_0e07e2b4). Цвет записи профиля
(тот, что потом читает `25 04`) всегда берётся из pkt[6..7]. Точная семантика spec
снимается одним захватом Armoury Crate. Клиент `set_key_color` приведён к этому формату
(старый слал echo+«range» — прошивка красила «клавишу №echo_lo» мусорным цветом, а ack
не матчился по echo).

`51 00` (0x0E07CA19) к слоям отношения **не имеет**: это мейлбокс LED-движка 0x23006FC8
(byte0 = код команды, 2 = «сменить профиль/режим», byte1 = аргумент 0..5, 6→0).

### 3.6 Дисплей

Команды `C0 81/83 …` с форвардом в sysctrl (0x0E07C0BA, буферы 0x23006F74, счётчик 0x23006754).
**Основной канал дисплея — семья 0x61–0x6B** (мега-хендлер 0x0E08CE6C через гейт 0x0E07A7AA):
страницы, время, CPU-метрики, виджеты/слоты, битмап. Состояние слотов/виджетов и IPC-сообщения
в sysctrl (0x1B/0x93/0x95/0x96/0x1C–0x1F/0x81) полностью разобраны в
**`analysis/PROTOCOL_STATUSBAR.md`** — там же битовая карта 0x23008BCE, форматы 0x24/0x6A/0x12
и путь до рендера.
Сам дисплейный движок (Calendar/SystemInfo/LightData/OL_Version) — в `m901_sysctrl.bin`
(адрес 0x00029000 app-window), общение между ядрами — icmsg/Zephyr IPC.

## 4. Прошивка (bootloader-протокол)

1. Хост открывает **APP** HID (PID 0x1C10, usage page 0xFF00/0xFF01) и шлёт magic `7B AA 'A' 'S' 'U' 'S' AA`
   → флаг 0xDEADBEEF @0x0E1A3600 → reboot.
2. Устройство перечисляется как **BOOT** HID (другой PID; bootloader в этот пакет не входит —
   он в защищённой области/ROM nRF54H20). Апдейтер настраивается аргументами
   `[APP_PID] [BOOT_PID] [BOOT_SIZE] [APP_SIZE] [APP_USAGE_PAGE] [BOOT_USAGE_PAGE] [PAGE_SIZE]`.
3. Передача: поток 64-байтных пакетов ( InterruptTransfer_WriteLen / SetInterruptTransferReadEventLen),
   логи: `[S] Bootloader Version = V…`, `Application Version = …`, `Read checksum...`,
   `Same FW Version! Skip Update...`, `leave_boot`, `=WR MGC CODE F`, `=EPwrong_size`, `CHK R ERR`, `= Suit Fail`.
4. Финал: проверка checksum, `FW Update Complete!`, команда `leave_boot` (выход из bootloader).

Файл, который заливается — ровно наш `M901_DEVICE_V07_00_30.bin` (SUIT-пакет целиком;
устройство само валидирует манифесты и раскладывает образы по 0x0006F000 / 0x00029000).
