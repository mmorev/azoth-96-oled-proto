# M901 (ROG Azoth 96 HE) — OLED: реестр виджетов sysctrl, 0x62/0x67, битмап, LED-биты

Дата: 2026-10-03. Базы: `m901_keyboard_app.bin` @ **0x0E066000**, `m901_sysctrl.bin` @ **0x0E0D5000**.
Дополняет `PROTOCOL_STATUSBAR.md` (механика слотов/статус-бара/рендера — там и только там),
`PROTOCOL_VOLUME.md` §6 (карта опкодов), `report.md` (USB-захваты).
Все адреса абсолютные. Декомпиляты: `decomp_kbd_wsl/`, `decomp_sysctrl_wsl/`, `decomp_handlers_wsl/`.

---

## 0. Главные выводы

1. **Named-сервисов в sysctrl ровно 5**: `AMOLED`, `DBG`, `SystemInfo`, `LightData`, `Data`
   (таблица @0x0E0F5444, запись 24 байта `{name, 0, get, set, 0, 0}`; все `get` — стабы).
   Отдельного «реестра виджетов» с id нет: виджеты — это страницы/состояния поверх этих сервисов.
2. **0x62 — второй (большой) битмап-протокол**: слот-заливка до 200 КБ (`62 00` begin /
   `62 01` чанки / `62 02` end → страница 7). **0x67 — «баннер»**: картинка 136..680 × 48 px
   для слота 0 (`67 00 [02]` begin, `67 01` чанки, `67 02` commit → [0x23014C34]=1 + таймер 30 тиков).
3. **RGB565 — little-endian** (младший байт пикселя первым). Доказательство: сплэш sysctrl
   (flash 0x0E0EE440) — гладкие серые ступени `0x0841=(1,2,1)`, `0x1082=(2,4,2)`, `0x2104=(4,8,4)`
   только при LE-интерпретации; весь канал до панели байт-прозрачен (memcpy → VPR-кольцо → DMA).
4. **Мета `01 00 e8 03`** — первые 4 байта потока данных чанков, keyboard-стороной НЕ парсится
   (копируется в поток как данные). Роль «1000 тиков» выполняет IPC-таймер [0x2300127C],
   запускаемый `67 02` (= 0x1E = 30 тиков, §5.3).
5. **`50 55` = commit**: фиксация RGB-стейта ([0x23006FC8]=4) + выталкивание очереди FB-канала
   на iface2 IN (`FB 03 …`) + перенос staged-буфера.
6. **`27`** — чистый геттер флага «GearLink-сессия активна» [0x2301D21C]; флаг ставит
   `74 00 [0/1]`, он же гейтит `C0 81`. В ответ на `27` устройство ничего не триггерит.
7. Тела писателей LED-битов (Caps/Num/Scroll) — **RAM-код, в образе отсутствует** (подтверждено
   сканом); найдены все инициализаторы: 4 группы по 3 колбэка (по одному на HID-интерфейс).

## 1. Реестр named-сервисов sysctrl (таблица @0x0E0F5444)

Формат записи: 6 слов `{ptr-имя, 0, get*, set*, 0, 0}` (thumb-биты сняты ниже). Таблица
заканчивается нулевой записью; `DBG`-запись — ровно как в старых заметках, но с 6-словным
шагом. Строки-имена: 0x0E0F3038 `AMOLED`, 0x0E0F3040 `DBG`, 0x0E0F3044 `SystemInfo`,
0x0E0F3050 `LightData`, 0x0E0F305C `Data`. Диспетчер SSF ищет имя и зовёт get/set
(get-слоты у всех — `bx lr` стабы 0x0E0DBC00/04/3C/40/44/48).

| # | Сервис | get | set | Что делает set (декомпилировано) |
|---|--------|-----|-----|----------------------------------|
| 0 | **AMOLED** | 0x0E0DBC40 (стаб) | 0x0E0DBC08 | `if (len > 0x41) return; memcpy(0x2F01137C, data, len)` — образ статус-бара (макс 65 Б = [+0] режим + 9 слотовых байт + резерв). Целевой буфер = литерал @0x0E0DBC18 = 0x2F01137D−1. Синхронизатор 0x0E0DC0E8 диффит (STATUSBAR §7.2) |
| 1 | **DBG** | 0x0E0DBC3C (стаб) | 0x0E0DBC04 (стаб) | оба стаба — сервис-заглушка |
| 2 | **SystemInfo** | 0x0E0DBC48 (стаб) | 0x0E0DBC4C | главный set-хендлер метрик, 9 подкоманд ([0] = pkt[0] запроса) — см. §1.1 |
| 3 | **LightData** | 0x0E0DBC44 (стаб) | 0x0E0DBC1C | список LED-данных (эффекты RGB): `[0]==0 → буфер A, ==1 → буфер B (A+len_A)`; `memcpy(buf+len, data+1, len−1); len += …; if (len > 0x149) dirty=1` (0x14A — лимит списка, 330 Б). Буферы/флаги: указатели 0x0E0E10A8..B0 |
| 4 | **Data** | 0x0E0DBC00 (стаб) | 0x0E0DBE50 | ответы на C0 81/83-форварды: только `data[0]==2`, свитч по `data[1]` (sub 0..0xE), каждая ветка собирает `{0x02<<8\|sub, payload}` и шлёт ipc_service_send (0x0E0E2D0C) обратно на keyboard-ядро — см. §1.2 |

### 1.1 SystemInfo set (0x0E0DBC4C) — подкоманды

Вход: `[0] = sub`, далее аргументы. Глобальные флаги: 0x0E0DBE14 (dirty[0..5] u32-массив),
0x0E0DBE18 = текущая страница, 0x0E0DBE40 = флаг спец-рендера.

| sub | Действие |
|-----|----------|
| 0 | `arg[1]` 0/1 → `*0x…ABC = 0/1; *0x…AC0 = 1` (вкл/выкл SystemInfo-виджета); 2 → вызов 0x0E0DE9FC + сброс 0x0E0DBE40; 3 → 0x0E0DE918 + сброс |
| 1 | **страница**: `*0x0E0DBE18 = arg[1]` (CPU/Fan/GPU/Usage/Freq/Volt — tbb в рендере), dirty=1, перечитывает данные (0x0E0DEDBC/DD8 → 0x0E0DBE20), затем ~800 итераций FUN_0e0e0728 (ожидание применения) |
| 2 | `*(*0x0E0DBE24) = arg[1]; *(ptr+1) = arg[2]` — 2 байта в структуру страницы; dirty=1 |
| 3 | `*(ptr+8) = u32 arg[1..4]; *(ptr+0xC) = u32 arg[5..8]` — два u32; dirty=1 |
| 4 | `memcpy(*0x0E0DBE28 + 0x2D8, arg+1, len−1)` — блок «Usage/страница» (тот же буфер, что Data sub 5 отдаёт хосту); dirty[2]=1 |
| 5 | `memcpy(*0x0E0DBE24 + 0x9F2, arg+1, len−1)`; dirty[3]=1 |
| 6 | `*0x0E0DBE0C = arg[1]; *0x0E0DBE10 = arg[2]`; dirty[4]=1 |
| 7 | **отправка битмапа**: репак 0x6E байт из трёх параллельных буферов (0x0E0DBE2C байты, 0x0E0DBE30 u16, 0x0E0DBE34 байты) в u32-записи `{b0, b1<<8, b2<<16, b3<<24}` → 0x1B8 байт; `buf[0]=7; memcpy(buf+1,…)`; отправка через vtable-вызов ipc (0x0E0E2D2A) |
| 8 | dirty[5]=1 (флаш) |

### 1.2 Data set (0x0E0DBE50) — ответный канал C0 81/83

`data[0]` обязан быть 2, иначе выход. Свитч по `data[1]`:

| sub | Источник payload | Размер | id ответа |
|-----|------------------|--------|-----------|
| 0 | `*0x0E0DC02C + 0x5A6` | 0xDC | 0x0200 |
| 1 | `*0x0E0DC02C + 0x2A4` | 0xDC | 0x0201 |
| 3 | (маленький) | 5 | 0x0102 |
| 4 | `*0x0E0DC02C + 0xEC` | 0xDC | 0x0402 |
| 5 | `*0x0E0DC03C + 0x2D8` | 0x6E | 0x0502 |
| 7 | репак 0x6E u16 (0x0E0DC040 пары с 0x0E0DC048) в 3-байтные записи `{b0,b1,b2}` | 0x14A | 0x0702 |
| 0xC | после FUN_0e0e1004; `*0x0E0DC02C + 0x45C` | 0x6E | 0x0D02 |
| 0xD | `*0x0E0DC02C + 0x682` | 0xDC | 0x0D02 |
| 0xE | `*0x0E0DC02C + 0x75E` | 0xDC | 0x0E02 |

Буферы +0x5A6/0x2A4/0xEC/… — те же, что читает рендер SystemInfo (0x0E0DF208:
значения вентиляторов/RPM с границами 1000/3500 и массивом @+0x5A6). Ответы совпадают
с наблюдаемыми в STATUSBAR §7.2 (sub0/1/4/13/14 → 0xDC, sub5 → 0x6E, sub7 → 0x14A).

### 1.3 Виджет-надписи Mail/Alarm/Calendar (sysctrl 0x0E0DB522)

`FUN_0e0db522(name_ptr, u8, u32)` с 5-м аргументом в **ip** (0/1/2): копирует на стек строки
`Alarm` (0x0E0F2FB4) и `Calendar` (0x0E0F2FBC), затем по mode:
- 0 → имя из arg0 (4 символа — `Mail`, строка 0x0E0F2FAC), X=0x44, len=7;
- 1 → `Alarm`, X=0x3E, len=9;
- 2 → `Calendar`, X=0x2C, len=8;
- 2-я ветка (ip==2) → выключение (сброс [0x2F025464]-стейта, флагов 0x0E0DB3D0..0x0E0DB420).

Общее: `memcpy(0x2F0240D4, name, len)`; [0x2F0240B4] = len; [0x2F0240B8] = 0x48;
[0x2F0240BC] = 0x32; [0x2F0240E8] = X; [0x2F0240EC] = 0x16; halfword [0x2F025464]:
`(v & 0xF) | 0x10`; [0x2F04E1E3] = 1 (dirty); tail-call рендера 0x0E0D7788.
Структуру 0x2F0240B4/D4/0x2F02341C читают функции текстового движка 0x0E0D7440-0x0E0D9B98.
Прямых BL-вызывальщиков в образе нет (зовётся по указателю из RAM-кода или неиспользуема).
Строки `=OL_CAL`, `=OL_Version`, `=OL_CKF/CKP/CKI`, `Temp.`, `Usage`, `Freq.` (0x0E0F2F04-0x0E0F2FA4) —
имена конфиг-переменных/лейблов этого же виджетового слоя.

## 2. Опкод 0x62 — большой битмап (ветки 0x0E08D394/0x0E08D572/0x0E08D59A)

Ветка 0x62 мега-хендлера 0x0E08CE6C (decomp_kbd_wsl/0e08ce6c). Гейт обычный
([[0x230086BC+0x513]]≠0 или [0x2301D250]≠0). Два режима геометрии в sub 0:

### 2.1 `62 00 <echo> [id:u16] [A:u16] [B:u16] [chunks:u16]`

- `id = pkt[4..5] u16`: (id−5)&0xFF < 0xFA → отказ, т.е. id ∈ {0..4, 0xFF…} — **номер слота**.
- Если `pkt[5] == 0` (id 0..4/0x00FF): `A = pkt[6..7]` обязан быть **0x88 = 136** (ширина),
  `B = pkt[8..9]` = высота (свободная).
- Если `pkt[5] == 1`: `B = pkt[8..9]` обязан быть **0x55 = 85** (высота), `A` = ширина (свободная).
- Ограничение кадра: `A*B*2 + 8 ≤ 0x32000` (≈200 КБ) — значит поток = пиксели + 8 байт заголовка.
- Далее — стандартный сброс сессии (как 0x61 01): экран off ([+0x513]=0), init-структур через
  0x0E088E00(0xF9, …), батарейный байт, сохранение конфига FUN_0e081988 (⚠ флеш-запись),
  `*DAT_0e08d6b0 = 1`, маркер сессии `0x62`, счётчик чанков `*DAT_0e08d6b8 = pkt[10..11] u16`.

### 2.2 `62 01 <echo=idx:u16> [idx_hi:u16] [58 Б данных]`

Аналог 0x61 02: индекс чанка = **u32 LE из pkt[2..5]** (echo + pkt[4]<<16 + pkt[5]<<24),
строго убывающий от chunks−1 до 0; данные с pkt[6] льются в VPR-кольцо 0x2FC03400
(FUN_0e08c110: слоты 0x1000 Б × 10, дескрипторы +0x10, done-флаг [ring+0xC]).
Последний чанк (idx==0) ставит флаг `[0x23014B14+0x34] |= 1 << [0x23000C9E]` (по номеру
текущего устройства) и глушит сессию; ACK-пейсминг — как у 0x61 (каждые 0x14 чанков).

### 2.3 `62 02 …` — END

Проверяет бит готовности ([0x23014B14+0x34]); переключает **страницу 7**:
IPC {0x13, dev, 7} + [0x23000C9F] = 7 + push 0x1B + батарейный байт. Страница 7 —
«кастомный битмап большого формата» (в сборщике 0x95 и STATUSBAR §8 она же фигурирует
как ненаблюдавшаяся).

## 3. Опкод 0x67 — баннер слота 0 (ветки 0x0E08D504/0x0E08D47E/0x0E08CFC2)

Диспетчер 0x67: sub 0 → 0x0E08CFC2, sub 1 → 0x0E08D504, sub 2 → 0x0E08D47E.
Все ветки требуют **[0x23000C98+9] == 0** (активный слот = 0).

### 3.1 `67 00 <echo> 01` — отмена/очистка баннера

[0x23014C2C]=0, [0x23014C30]=0, [0x2301D24F]=0; ответ без старта сессии.

### 3.2 `67 00 <echo> 02 [w:u16] [h:u16]` — BEGIN

- `w = pkt[4..5]` u16 LE ∈ **[0x88..0x2A8] = [136..680]**; `h = pkt[6..7]` обязан быть **0x30 = 48**.
- Инициализация VPR-кольца 0x2FC03400 ([ring]=1, слоты/дескрипторы в 0), 0x0E088E00(0xF9,…).
- Состояние сессии: [0x2301D24C]=0x67 (маркер), [0x2301D24B]=1, [0x23014BFC]=0x30 (счётчик
  чанков = 48), [0x23014BF8]=5, [0x23014BF4]=0 (ACK-счётчик, ACK каждые 0x14 чанков),
  [0x23014BF0]=0xFF.
- Параметры баннера: **[0x23014C28] = 2** (mode), [0x23014C24] = pkt[5] (низ байта w),
  [0x23014C30] = w, [0x23014C2C] = 0x30.
  ⚠ В PROTOCOL_STATUSBAR.md §5 поля 0x23014C24/28 значились «нибблы времени» — на самом деле
  это параметры баннера (мод/аргумент), читаются также сборщиком слота 0 и качелькой.
- IPC **{0x21, mode, pkt[5], w_lo, w_hi, …, len 7}** в sysctrl.
- Ответ-эхо с аргументами.

### 3.3 `67 01 <echo=idx:u16> …` — чанки

Индекс убывающий (48−1 → 0), данные с pkt[6] → FUN_0e08c110 (кольцо). На каждый чанк,
кроме каждого 20-го, ответ-эхо без ACK-байтов; на границах — эхо с `AA FF` в pkt[4..5]
(= 0xFF, 0xAA в старших байтах u32-заголовка ответа). IPC-конверт уведомления — id **0x167**
(у 0x61-потока — **0x261**), буфер 0x23014BE4: {id, idx u16, len, …}.

### 3.4 `67 02 …` — COMMIT (закрытие открытого вопроса про мету)

- Требует [0x23014C28] ∈ {1, 2} (mode от begin); при mode==2 — [0x2301D24F]==0.
- **[0x23014C34] = 1** (если не был 1) — «спец-рендер слота 0» (баннер) + push 0x1B.
- Копирует **pkt[4..0x1F] (28 байт) в [0x23014C01]** — блок параметров баннера.
- **Таймер: [0x2300127C] = 0x1E (30 тиков)** + IPC {0x1E, …}. Тикер 0x0E08CC18 при достижении
  нуля обнуляет [0x23014C34] и перерисовывает (0x0E08CBB0) — баннер живёт ~30 тиков.
  Гипотеза из задачи («[0x23014C34]=1 + 1000 тиков») подтверждена наполовину: счётчик = 1 ✓,
  длительность задаётся таймером, но = 30 тиков, а не 1000.

## 3.5 Связь с метой `01 00 e8 03` (закрытие вопроса)

Ветка 0x61 sub 2 для чанка #615 (idx == total−1, 0x0E08D75C) копирует данные **как есть**
с pkt[6] (`FUN_0e08c110(pkt+6, 58, 0)`) — мета не парсится keyboard-ядром и не влияет на
[0x23014C34]. Это просто первые 4 байта потока, уходящие в sysctrl/панель (мл. байты
`01 00` = флаг/режим, `e8 03` = 1000 LE — вероятно, параметры оверлея панельного контроллера;
итоговый поток 616×58 = 35 728 = 4 мета + 35 696 пиксельных + 28 паддинга).
Семантика «показать N тиков и вернуть виджеты» на host-уровне реализуется связкой
`67 02` (или `51 5C`-семейство) + автотаймер, а не метой.

## 4. RGB565 byte order — ЗАКРЫТО

**Младший байт пикселя идёт первым (u16 LE, стандартный RGB565-сериализация).**

Доказательство (три независимых):
1. Сплэш sysctrl @flash 0x0E0EE440 (копируется в FB @0x0E0D87DA без преобразования):
   начала строк дают последовательность серых `0x0000, 0x0020, 0x0841, 0x0861, 0x1082, 0x2104…`,
   т.е. R=G=B/2 ступени (1,2,1)→(2,4,2)→(4,8,4) — гладкий антиалиасинг ТОЛЬКО при LE.
   В BE те же байты = `0x2000, 0x4108, 0x6108…` — серости не получается.
2. Канал доставки байт-прозрачен: FUN_0e08c110 (keyboard) — memcpy; sysctrl-машина
   0x0E0DD8A4 — DMA-копии 0x400-чанков в 0x2F892000; ни одного rev16/revsh/swap на пути
   (скан инструкций).
3. Захваты white/black (`FF FF`/`00 00`) инвариантны — порядок по ним не определить, но он и
   не нужен: GearLink льёт LE, панель принимает LE.

## 5. `50 55` commit (0x0E07D65A) — ЗАКРЫТО

Хендлер 0x0E07D65A делает три вещи:

1. **RGB-стейт**: если [0x23006FC8] != 4 → [0x23006FC8] = 4; u16 [0x23006FC8+8] |= 0x100
   (сохранив биты 0xF2xx); [0x23006FC8+9] |= 2. (0x23006FC8 — база режима/слоя RGB,
   `51 00` пишет [0x23006FC8+1].)
2. **Staged-конфиг**: если флаг [0x2301D21B] ≠ 0 → memcpy(0x2300CB1C ← 0x23006E64,
   [0x23006E5C] байт), [0x23006E5C] = 0, [0x2301D219] = 1, [0x2301D21B] = 0.
3. **Выталкивание FB-очереди**: пока [0x23006E10] (остаток) > 0, порциями ≤ 0x20:
   буфер {u16 0x03FB, idx<<6\|len, …} → **0x0E091E90(2, …)** = IN-репорт на iface2
   (`FB 03 <idx<<6|len> …` — тот же формат, что лог-канал `FB 03`, PROTOCOL_VOLUME §7).
   Источник — кольцо 0x23006E1C, idx — [0x23006E18]; на успех ptr += len; при остатке 0 —
   флаг сбрасывается.

Итог: `50 55 00 00` — «фиксируй пачку»: применить режим RGB + отдать хосту накопленные
лог/ответные данные. Смысл в captures («финализатор пачки») подтверждён; опасности нет
(кроме износа флеша от `FUN_0e081988` в предшествующих командах пачки).

## 6. `27` и флаг [0x2301D21C] — ЗАКРЫТО

- **0x27 (0x0E07BF9E)** — чистый геттер: ответ `27 <sub> <echo> [0x2301D21C]`. Ничего не
  триггерит; «пинг GearLink» = проверка живости сессии хостом.
- Писатель — **`74 00 <echo> [v]`** (0x0E07AFC3): если pkt[4] != флага → флаг := pkt[4];
  при включении (0→1) — IPC-конверт {0x51, 0, 0} (0x0E09217C), при выключении — ветка
  0x0E07D574. Прочие sub 0x74 → ветка 0xB5/0xFF ([0x23000CA2], PROTOCOL_STATUSBAR §6).
- Потребитель — **`C0 81`** (0x0E07A7EA): при флаге==0 чтение памяти через sysctrl запрещено
  (→ 0x0E07D43C). Т.е. флаг = «авторизация vendor-сессии»: GearLink ставит его конфиг-пачкой
  и периодически пингует `27`.
- Соседний кластер: [0x2301D219] / [0x2301D21B] — флаги staged-буфера `50 55` (§5).

## 7. Писатели per-device LED-битов (Caps/Num/Scroll) — что удалось установить

Адресаты: биты `[0x23014B14 + dev*8]` — bit6 @+0 (иконки 0x1A/0x1B), bit5 @+2 (0x1E/0x1F),
bit4 @+3 (0x1C/0x1D) (STATUSBAR §7.3). Flash-писателей нет (скан lsl#3-паттернов и литералов).

Найдено в .data-инициализаторе (flash-хвост):

| LMA | Значения (RAM thumb-указатели) | RAM-адреса группы |
|-----|--------------------------------|-------------------|
| 0x0E0C6FB8 | 0x23001B29, 0x23001B39, 0x23001B47, (dup 0x23001B29) | группа 1 |
| 0x0E0C703C | **0x23001BAD**, 0x23001BBD, 0x23001BCB, (dup) | группа 2 (переменные 0x23001BA4/AD/B6/C4 из задачи) |
| 0x0E0C70C0 | 0x23001C31, 0x23001C41, 0x23001C4F, (dup) | группа 3 |
| 0x0E0C7144 | 0x23001CB5, 0x23001CC5, 0x23001CD3, (dup) | группа 4 |

Структура: **4 одинаковые группы (по числу HID-интерфейсов hid_dev_0..3) по 3 колбэка**
(+0x10, +0xE байт; шаг группы 0x84) — шаблон Zephyr HID-драйвера {in_cb, out_cb, err/idle_cb}.
Тела колбэков — **RAM-код, отсутствующий в образе**: LMA-копия не найдена ни в хвосте

RAM-код, вероятно, грузится загрузчиком/SUIT вне этого файла.

Следствие: точный маппинг «байт LED-репорта iface0 → бит/лок» кодом не подтверждается;
остаётся поведенческая гипотеза (5 бит OUT-репорта iface0 по HID-спеке: Num, Caps, Scroll,
Compose, Kana → три бита per-dev). Таблица вызовов через указатели: {0x23001A50, 0x230019FC,
0x230019A8, 0x23001954, 0x23001900} @0x0E0A2218/0x0E0A2270 — таблица RAM-функций стека
(шаг 0x54), к LED-битам напрямую не относится.

## 10. Метрики 0x66, метки SystemInfo и реальная семантика C0 81/83 (разобрано 2026-10-03)

Итог сверки захватов (все *.pcap) с декомпиляцией; закрывает вопрос «есть ли RAM/VRAM».

### 10.1 Формат 0x66 — пары {селектор, u16}, НЕ байтовые поля

Захваты 08b (покой) и 09 (нагрузка): `66 00 01 00 | 00 00 14 00 | 01 00 30 00` и
`…| 00 00 48 00 | 01 00 46 00`. Т.е. полезная нагрузка — **две пары
{sel:u8, rsv:u8, val:u16 LE}**: sel 0 = usage % (0x14=20, 0x48=72), sel 1 = temp °C
(0x30=48, 0x46=70). Валидация хендлера (0x0E08CE6C case 0x66): нибблы sel ≤ {hi 4, lo 5}
для обеих пар — пространство селекторов **0..5** (второй байт пары rsv=0; при sel-байте
вида 0x?y ограничения на оба ниббла). GearLink пушит event-driven и **только при живом
экране** (05-system: 100% CPU при спящем OLED — ни одного push).

> **ИСПРАВЛЕНО:** байт pkt[7] — это **старший байт u16 usage**, а не «RAM %» (в захватам
> всегда 0x00). Старый клиент писал туда ram — при ram≠0 значение usage портилось
> (usage + ram*256). Клиент исправлен: `send_cpu_usage(usage, temp)`.
> «Слот 3 = CPU+RAM» — тоже устаревшая трактовка: двойной индикатор = **temp + usage**
> (тот же набор, что у виджета CPU в GearLink).

### 10.2 Структура 0x23000C98 и кто её пишет

`12 00` копирует 16 байт оттуда (0x0E07DCA2): `30 00 07 00 06 00 …` = +0 temp, +2 usage,
+4 **третья метрика** = 6. Значения не меняются ни в одном захвате за 2+ часа → это
«последние запушенные» значения (с труду часом ранее BOOT-сессии GearLink). Селектор→поле:
sel 1 → +0, sel 0 → +2; третья метрика (селектор ≥ 2, в захватов не пушится) → +4;
при простое = 6 — похоже на **volt×10 (0.6 В) или freq/100 (600 МГц)**, различить
нечем. **Писателя +0..+5 во flash-образе нет** (полный sweep с трекингом базового регистра
+ верификация пулов; все 97 ссылок на 0x23000C98 в декомпиляте — чтения статус-полей
+6..+0xC) — обновляет RAM-код, как и LED-колбэки (§7).

### 10.3 Метки — фиксированные строки во флеше sysctrl; RAM/VRAM строк НЕТ

Полный скан строк обоих бинарников: **ни одного вхождения RAM/VRAM как подписи метрик**
(«RPM» тоже нет; подпись у вентиляторных значений — «Fan»). В sysctrl инлайн-литералы
функции текстового слоя SystemInfo (0x0E0D7818..0x0E0D7AE0, хвост — текстовый рендер
0x0E0D7788):

- заголовки страниц (литералы/арифметика в прологе): `CPU` (0x0E0D7AF4, слово
  0x00555043), `Fan` (0x006E6146), `GPU` (0x00555047 @0x0E0D7AFC), `DRAM` (пул
  0x4D415244 @0x0E0D7CD8), `VRM` и `CHA` — построены арифметикой из литерала GPU
  (0x00555047−0x7F800+~0x5F0 = «VRM\0», далее −0xC0000−0xA13 = «CHA\0»);
- подписи значений: `Temp.` (0x0E0F2F70), `Usage` (0x0E0F2F78), `Freq.` (0x0E0F2F80),
  `Volt` (0x0E0D7B1C, inline, 4 байта без NUL), `Fan` (шаблон с заголовком).

> **ИСПРАВЛЕНО:** ранее строка читалась как «/CPU» — это артефакт парсинга: байт 0x2F
> перед «CPU» — старший байт пула 0x2F0112E0. На дисплее видно «CPU0» — цифра берётся
> из байта [+3] конфиг-записи (0xFF = без цифры) и конкатенируется с заголовком
> (strlen/strcat-путь 0x0E0E1CFC/0x0E0E1D54). Подписи рисуются из флеш-строк; текстовые
> структуры (0x2F0240B4/D4/C0/F0/0x414C/0x4128, та же семья, что у сеттера
> Mail/Alarm/Calendar 0x0E0DB522) получают строки memcpy-копией при конфигурировании.

### 10.3.1 Конструктор страниц SystemInfo — это монитор датчиков МП (CPU/GPU/VRM/CHA/DRAM)

Функция 0x0E0D7818 обходит **таблицу конфигурации страниц в RAM sysctrl @0x2F0112E0**
(записи по 4 байта, до 16: byte[+2] = тип, byte[+3] = номер инстанса):

| byte[+2] & 0xF0 | Заголовок | Смысл |
|---|---|---|
| ≤ 0x0F | CPU+цифра | per-core CPU (CPU0, CPU1…) |
| 0x10 | GPU | видеокарта |
| 0x20 | VRM | датчик VRM |
| 0x30 | DRAM+цифра | память (DIMM-телеметрия, DRAM0…) |
| 0x40 | CHA+цифра | корпусные вентиляторы (CHA_FAN) |

Подпись значения — по byte[+2] & 0xF (ПОПРАВЛЕНО по захвату 11-mon-widgets: в
прологе конструктора шаблоны лежат [sp+0x20]=«Usage», [sp+0x28]=«Temp.»,
[sp+0x30]=«Freq.» — case 0 берёт [sp+0x20]): **0=Usage, 1=Temp., 2=Freq.,
3/4=Fan, 5=Volt**. Пороговые 1000/3500 в дата-пути (+0x5A6) — диапазон RPM.

Это виджет **аппаратного монитора материнской платы** (как сенсорная панель Armoury
Crate для ROG-плат): прошивка поддерживает БОЛЬШЕ тайлов, чем GearLink шлёт на клавиатуру
(CPU-набор) — VRM/CHA/DRAM-страницы в прошивке есть, просто хостом не задействуются.

### 10.3.2 Диспетчер режимов AMOLED = ПРОТОКОЛ ВИДЖЕТОВ (пересмотрено 2026-10-03, поздн.)

**КЛЮЧЕВАЯ ИНТЕРПРЕТАЦИЯ (исправляет §10.3.2 раннюю и STATUSBAR §7.1): «IPC id» из
клавиатуры — это и есть mode-байт диспетчера 0x0E0DC0E8.** Push 0x0E08CBB0 шлёт конверт
`{0x1B, slot, …}` (первый байт = id = mode) → AMOLED set → memcpy в 0x2F01137C → tbb.
Полная карта режимов (из tbb @0x0E0DC100 + хендлеры 0x0E0DC150..0x0E0DC6xx):

| mode | Хендлер | Источник на keyboard | Действие |
|---|---|---|---|
| 0x12 | 0x0E0DC450 | `0x68` → 0x0E08C3FC `{0x12, v}` | **гейдж**: `[0x2F0134D8+1] = v*128/100` (bar 0–128). `0x68` квантует v в {0,25,50,75,100} (клампы 0x0E07D468/DBAA) — **яркость 4 ступенями**, хранится per-page в `[0x230086BC+0x4B2+page]` |
| 0x13 | 0x0E0DC440 | `0x61 00` {page} | page → `[0x2F0134D8+0/+2]`, bl 0x0E0DB094 |
| 0x14 | 0x0E0DC400 | `51 60 <u16>` → 0x0E08C58C `{0x14, lo, hi}` | 9-битная **маска активных слотов статус-бара** → LUT 0x2F0112D4 (set=5−i, clear=0xFF) + `[0x2F04E1C8]`; будит экран при v≠0 |
| 0x16 | 0x0E0DC3E0 | хелпер 0x0E08C548 `{0x16, b, u16, u16, b}` — **вызывальщиков нет (dead)** | 13-битное сравнение в 0x0E0DB79C (похоже на media-progress; материнский сценарий) |
| 0x18 | 0x0E0DC3CA | `51 0C` (громкость) | u16+байт → 0x2F0134D4, OSD |
| 0x1B | 0x0E0DC308 | push 0x0E08CBB0 `{0x1B, slot, [C34], 0, page}` | slot → 0x2F04E1DD, [C34] → 0x2F04E1DC, page → 0x2F0134D8; slot==4 → спец-путь |
| 0x1C | 0x0E0DC300 | `0x63` (время) | 7 байт → текст-структура 0x2F023414 (писатель 0x0E0DB490) |
| 0x1D | 0x0E0DC2EC | `0x64 {val, on}` | **тайл слота 2**: val → table[0] (писатель 0x0E0DB4CC), on → бит2 0x2F025460; dirty при slot==2 |
| 0x1E | 0x0E0DC2E4 | `0x66 {selA,digA,valA u16,selB,digB,valB u16}` | **тайлы слота 3**: 8 байт → 0x2F0112E2 (писатель 0x0E0DB4EC), dirty при slot==3 |

Ранний вердикт «режимы 0x1B–0x1E — мёртвый код материнского сценария» — **ОТМЕНЁН**:
это штатные апдейты `0x64`/`0x66`/push'ей. «Мёртв» только 0x16.

**Таблица 0x2F0112E0 — это таблица ТАЙЛОВ-индикаторов** (не «конфиг страниц»): записи
по 4 байта `{value[2], type|label, digit}`, конструктор 0x0E0D7818 строит из них заголовки.
Следствие: **байты selA/selB в `0x66` (валидация: hi≤4, lo≤5) — это ВЫБОР ТИПА ТАЙЛА**:
hi-ниббл → заголовок {0=CPU, 1=GPU, 2=VRM, 3=DRAM, 4=CHA} (+цифра из байта digit, 0xFF =
без цифры), lo-ниббл → подпись значения {0=Temp., 1=Usage, 2=Freq., 3/4=Fan, 5=Volt}.
То есть `66 00 01 00 31 00 <u16> 30 01 <u16>` нарисует тайлы «DRAM0/Usage» и «DRAM1/Temp.»
с нашими значениями. Пэйринг value↔type в потоке записей сдвинут на пол-записи
(entry_i.type приходит с push'а i, value — с i−1) — точную привязку закрыть живым тестом.

**По батарее хоста: виджета НЕТ.** Полная карта каналов хост→OLED (таблица выше + битмапы
0x61/62/67/6B) не содержит ни батарейного заголовка (только CPU/GPU/VRM/DRAM/CHA/Fan),
ни подписи (Temp./Usage/Freq./Fan/Volt), ни иконки: иконка батареи в статус-баре — только
самой клавиатуры (14+уровень из [0x2301D226], писатели — ADC-кластер 0x0E0805xx/0x0E095Bxx).
Батарейные сабы `51 2C–0x3A/0x58/0x59` (0x4B0/0x4B1/0x834) — стейт заряда самой клавиатуры.

### 10.5 Захваты 10-battery-toggle / 11-mon-widgets (2026-10-03) — ground truth

**Захват 1 (включение виджета батареи)** — канал батареи хоста НАЙДЕН:

```
6a 00 00 00 02 01     включить слот 2
6a 01 00 00 02 00     выбрать слот 2 (×2)
24 01                 → 24 01 … 02 (подтверждение)
64 00 00 00 63 00     ЗНАЧЕНИЕ ТАЙЛА СЛОТА 2 = 99 (батарея ноутбука 99%)
68 00 00 00 64 00     яркость 100
50 55 00 00           commit
(+ повтор 64 … 63 через 3 с — event-driven)
```

⇒ **виджет «батарея» = слот 2 + `64 00 <echo> <процент> <on>`** (mode 0x1D → table[0]).
Подписи «Battery» в прошивке нет — тайл показывает число (заголовок/подпись тайла
определяются selA последнего пуша 0x66, см. §10.3.2).

**Захват 2 (4 одинарных + 1 двойной мониторинговых виджета, 98 с):**
- настройка слотов циклом: `24 01` → слот 1 → push `63` (время; слот 1 = часы!),
  слот 2 → `64` (батарея), слот 3 → `6a` enable/select двойного;
- маска `24 02` = {1,2,3} — одинарные виджеты СВОИХ СЛОТОВ НЕ ПОЛУЧАЮТ, идут пушами
  `0x66` в таблицу тайлов;
- **все пушы `0x66` (echo=1, второй байт echo-пары=00):**

| t | selA digA valA | selB digB valB | что это |
|---|---|---|---|
| 60.4 | 01 00 **50** | 00 00 0 | одинарный **Usage** = 50% |
| 65.8 | 01 00 **50** | 00 00 0 | повтор |
| 67.3 | 00 00 **7** | 01 00 **50** | двойной: **Usage 7% + Temp 50°C** |
| 70.2 | 05 00 **550** | 00 00 0 | одинарный **Volt** = 550 (5.50 В при /100) |
| 70.8 | 01 00 **50** | 00 00 0 | usage снова |

⇒ **единицы (уточнено захватом 12-swipe-events): Usage = %, Temp = °C, Freq = МГц
(sel 02, val 1989–1997 ≈ 2.0 ГГц), Volt = мВ (sel 05, val 525–981 = Vcore ноутбука)**.
Подтверждена карта lo-нибблов селектора: **0=Usage, 1=Temp., 2=Freq., 5=Volt** (уточняет
§10.3.1: 0 и 1 были переставлены). Цифра инстанса (digA/digB) = 0 → заголовки вида «CPU0».
Push'ов с hi-нибблом ≠0 не было — все виджеты GearLink = «CPU*»; заголовки GPU/VRM/DRAM/CHA
(hi 1–4) хостом не используются и доступны нам через `0x66` (метод `send_metric` в клиенте).

### 10.6 Сервисный канал iface1 (0xFFC0, Report ID 3) и GearLink как движок слайдшоу
(захват 12-swipe-events, 116 с, 2026-10-03)

**20-байтный IN-канал (ep 0x83) — это зеркало внутренних событий хосту**:

```
03 <type> 00 00 <payload…>        type = тот же id, что в keyboard→sysctrl IPC!
  0x93 — смена слота (payload[4] = новый слот; в кадре 03→02 = уход с мониторинга)
  0x95 / 0x96 — состояние/контент виджета (payload[4] = 0x30); стрим ~2 Гц
  0x71 — профиль/стейт дисплея (payload[4] = 0x80 … 0x00)

  > **УТОЧНЕНО (2026-10-05, `PROTOCOL_GESTURES.md`):** 0x95 = heartbeat состояния
  > виджета (~0.86 с) И одновременное «зеркало» жеста ВВЕРХ (байт-в-байт совпадают);
  > 0x96 = событие жеста ВНИЗ (отправляется только им — потому и видно на шине);
  > 0x94 = дабл-тап. Смена слота хостом детектится по 0393.
```

**GearLink — движок слайдшоу мониторинга.** На эти события (и/или по своему таймеру,
в среднем раз в ~1.8 с на протяжении всех 116 с) он пушит `0x66`, циклически меняя
селектор: freq(02) ↔ volt(05) ↔ … **«Страниц» на устройстве нет** — один и тот же тайл
таблицы 0x2F0112E0 перезаписывается новым селектором+значением. Подтверждено
пользователем: после убийства процессов GearLink индикатор замер на «CPU0 Usage 10%»,
вертикальные свайпы перестали что-либо делать.

⇒ **«Листание» мониторинга = свойство GearLink, не прошивки.** Свайп тачскрина до
прошивки дисплея не доходит вообще (в локальном диспетчере жестов слот мониторинга —
redraw-only, §10.5.1); событие уходит хосту по каналу 0x95/0x96, и уже GearLink решает,
какой метрикой перезаписать тайл. «Нестабильность свайпов» — наложение собственного
цикла GearLink (~2 с/страница) на ручные свайпы.

**Следствия (всё программно, GearLink не нужен):**
- «перелистывание страницы» = `send_metric(sel, 0, value)` с другим селектором;
- «слайдшоу мониторинга» = цикл `send_metric` по селекторам 0x00/0x01/0x02/0x05
  (используя живые значения или свои);
- полностью свои заголовки: hi-ниббл 1..4 = GPU/VRM/DRAM/CHA (тест `send_metric(0x31,0,42)`
  → «DRAM0 Temp 42» всё ещё pending);
- канал 0x95/0x96-событий можно слушать в своём софте (те же 20-байтные репорты) —
  источник событий «пользователь смотрит/переключает» для двусторонней синхронизации.

### 10.5.1 UX-модель экрана (подтверждено пользователем 2026-10-03, дополнено)

- **Влево-вправо (свайп по тачскрину)** — переключение групп виджетов: батарея → часы →
  индикаторы (т.е. слоты 2 → 1 → 3/4).
- **Вверх-вниз внутри «индикаторов»** — страницы: «CPU0 Usage» → «CPU0 Temp» →
  «CPU0 Volt» → «CPU0 Freq» → «CPU0 Usage+Temp». Пять «виджетов» GearLink — это пять
  СТРАНИЦ одного индикаторного слота (потому одинарные не получили слотов — их значения
  идут пушами 0x66 в таблицу тайлов 0x2F0112E0, страница выбирает тайл).
- Наблюдение на экране (живое): «CPU0 Usage 12 %» / «CPU0 Temp 60 C» — тайлы
  sel=0x00/0x01, заголовок «CPU0» = hi-ниббл 0 + digit 0. ⇒ Заголовок и подпись тайла
  полностью задаются байтом селектора 0x66; тест `send_metric(0x31, 0, 42)` должен дать
  «DRAM0 Temp 42».
- Слайдшоу: `6a 01 <slot>` реально переключает экран (подтверждено), метод
  `M901.slideshow([slots], interval)` в клиенте.

**Тачскрин — поведение (наблюдения пользователя, 2026-10-03):**

- **Авторотации страниц НЕТ** (проверено: в простое без ввода страницы не меняются;
  таймер простоя [0x2300128C] = 30 тиков автоповоротом не занимается).
- Страницы листаются **только свайпами по тачскрину** (не качелькой). Жест обрабатывается
  локально (в USB-трафик не попадает): декодер Δx/Δy 0x0E0810xx → диспетчер 0x0E08D84C,
  modes 3..6 = направления.
- **Действие вертикального свайпа зависит от текущего слота** (диспетчер 0x0E08D8B0
  свитчит по [0x23000C98+9]):
  - часы/календарь — переключение формата времени 12/24ч (работает ~95%);
  - батарея — переключение отображения % ↔ значок (работает ~95%);
  - мониторинг — **в прошивке жест-хендлер слота 3 — только перерисовка**
    (0x0E08D868 → сбор состояния + IPC 0x95, БЕЗ смены страницы), а карусель страниц
    (индекс 0..4 с wraparound @0x23019014, код 0x0E093F9E) находится в «особом» слоте 4
    (0x0E093F58 = сброс карусели при входе). Т.е. листание страниц мониторинга свайпом
    прошивкой на этом слоте НЕ реализовано напрямую — редкие срабатывания (1 из ~10),
    видимо, приходятся на другой путь/неверно распознанный жест.

  > **ИСПРАВЛЕНО (2026-10-05, `PROTOCOL_GESTURES.md`):** карта направлений утверждена:
  > ВВЕРХ = mode 3 → IPC 0x95, ВНИЗ = mode 4 → IPC 0x96, ВЛЕВО/ВПРАВО = mode 5/6 →
  > слот +1/−1 (IPC 0x93). На слоте 3 ВВЕРХ шлёт конверт, байт-в-байт равный
  > периодическому стриму 0395 (~0.86 с) — «вверх» хостом систематически невидим
  > (это НЕ нестабильность), а «1 из ~10 срабатываний» — это доходящие ВНИЗ (0396),
  > на которые GearLink листает метрику. «Карусель» @0x23019014/0x0E093F9E — не
  > страницы мониторинга, а кольцо истории KPS нативного тайла слота 4 (5 ячеек,
  > IPC {0x25, total, max}); вертикальный жест на слоте 4 её СБРАСЫВАЕТ (0x0E093F58),
  > а не листает. Листание назад хост-driven страниц в прошивке отсутствует by
  > design; свободный канал для «назад» — дабл-тап → `03 94` (0x0E08DB58).
- **Нестабильность**: с закрытым GearLink лучше (согласуется с гейтом wake-флага
  [0x2301D249] — его ставит `0x65`, который шлёт GearLink, и при ненулевом флаге
  диспетчер жесты молча ест), но на мониторинге всё равно ~1/10 — по ощущению
  пользователя виноваты постоянные обновления данных и/или калибровка тача (быстрые
  подряд свайпы листают надёжно). Кодовой коррелят: хендлер мониторинга — redraw-only,
  частые перерисовки + жест «съедается» перерисовкой.

  > **ИСПРАВЛЕНО (2026-10-05):** по коду `0x65` с v≤2 СТАВИТ гейт, а с v>2 (в т.ч.
  > `65 FF`, который шлют GearLink и прототип) — СНИМАЕТ; «глухие» жесты — это хвост
  > диспетчера при пробуждении экрана ([0x23002348]==0 → гейт=1) и сам wake-гейт.
  > «~1/10» — не потерянные жесты, а асимметрия 0396/0395 (исправление выше).
- Вывод: тач-UX не полагаться, управление страницами делать программно
  (`slideshow`/`select_slot`); при желании жесты можно блокировать совсем через
  `wake_display()` (ставит флаг-гейт). Программная смена страниц мониторинга —
  перспективный неизученный путь (карусель 0..4 в RAM @0x23019014, писатели
  0x0E093F58/0x0E093F9E — нетривиально; альтернатива — слайдшоу по слотам через `6a 01`).

  > **УТОЧНЕНО (2026-10-05):** «карусель 0..4» = KPS-кольцо тайла слота 4
  > (`PROTOCOL_GESTURES.md` §4), к страницам мониторинга отношения не имеет;
  > страницы мониторинга — состояние хоста (селекторы пушей 0x66), программная
  > смена = следующий пуш 0x66 с другим селектором.

### 10.4 C0 81/83 — НЕ произвольная память (исправление риск-таблиц)

Декомпиляция 0x0E07C0AA + резолв пулов показывает совсем не read/write по адресу:

- оба саба — **staging между двумя фиксированными буферами**:
  источник/стейт **0x2300CB20** (зона собранного пакета/конфига) ↔ приёмник
  **0x23006F74** (IPC-буфер форварда в sysctrl, см. PROTOCOL.md §3.6), счётчик
  **0x23006754** (+ байт-оффсет [0x23006F74+0xf]);
- **C0 81** — 60-байтными чанками **читает** стейт 0x2300CB20 в буфер ответа
  (`C0 82 <offset>`), гейт = флаг GearLink [0x2301D21C] (`74 00 … 01`);
- **C0 83** — **пишет** в staging (memcpy 0x2300CB20 → 0x23006F74, размер = счётчик<<2)
  с границами (`(arg>>8 & 0xF0)==0x10` → отказ); дальше стандартный форвард в sysctrl;
- после обеих веток — обновление LED-битов (FUN_0e086418 по байтам).

На sysctrl-стороне чтения тоже ограничены: Data-сервис отдаёт **фиксированные окна**
метрик (+0x5A6/+0x2A4/+0xEC/+0x682/+0x75E от *0x0E0DC02C, по 0xDC) — адресного
произвольного доступа нет нигде. Риск C0 83 понижаем с «высокий» до **средний**
(живой конфиг-путь форварда — незнакомые payload могут переключить настройки
sysctrl, но в чужую память не пишут). Прежняя формулировка «произвольная память —
высокий риск» была гипотезой без декомпиляции.

### 10.4.1 Следствия для «RAM/VRAM на экране»

- **Как значение** — можно уже сейчас: пуш 0x66 кладёт любое u16 в usage/temp-слоты,
  двойной индикатор и страница /CPU покажут число под подписью Usage/Temp.
- **Как подпись** — только патчем sysctrl (переподпись SUIT на стоковом устройстве
  невозможна) или записью строк в текстовые структуры sysctrl RAM (0x2F0240B4-семья) —
  а такого канала в разобранном протоколе нет (C0 83 в sysctrl-память не пишет).
  Пути к конфигурации страниц через AMOLED-режимы 0x1B–0x1E с клавиатуры тоже нет —
  см. §10.3.2 (мертвый код материнского сценария).
